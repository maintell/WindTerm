## 1. 一句话现状

44 条 P0 里 **19 条完成 / 19 条部分 / 6 条未做**。终端（SSH/本地）、SFTP 文件管理、
隧道、保险库与密钥、设置与键位、内嵌编辑器这些主链路都能用，端到端验收全绿
（**项数不写死**，以自己跑出来的 `N/N 项通过` 为准；`-WithE2e` 一轮约 10 分钟）。
**未做的 6 条里有 5 条属于「远程桌面（RDP）」与「打包发版」两块整功能**，不是半成品。

## 2. 怎么验（一条命令）

```powershell
pwsh ./scripts/check-all.ps1            # 单测 + clippy 零告警 + 文档对账（约 40 秒）
pwsh ./scripts/check-all.ps1 -WithE2e   # 再构建并跑端到端（约 10 分钟）
```

它会先构建带 `e2e-mock` 的产物再跑 e2e——**不要**绕过它直接 `node scripts/e2e-desktop.mjs`，
那样可能验的是上一版二进制。预期输出：单测全绿（**项数会随用例增长，不写死**）、
clippy 零告警、文档对账 PASSED、端到端 `N/N 项通过`，退出码 0。

## 5. 已知技术债与风险（都写在这里，别当没有）

1. **SFTP 连接池是串行化的**：同一台机器同一时刻只跑一个 SFTP 请求。这是刻意的——
   `russh_sftp::SftpSession` 的方法取 `&self`，并发会错配应答（实测随机卡死）。要真并发得在库层做请求队列。
2. ~~**跳板机缓存只覆盖单跳**~~ **已补齐（2026-11-08）**：单跳与多跳并成一条路径，缓存键是整条链
   （单跳时退化成原来的键，逐字节不变），缓存最后一跳的连接；e2e 读链上第一跳 mock 自己的
   会话计数，同一条两跳链再连一次不新建会话。**同轮修了两个真缺陷**：① 链的顺序反了——
   `resolve_jumps` 把「用户选的跳板会话」排第 1 跳，真实网络里等于直连最内层那台，现在按
   「离本机由近到远」排（`chain_in_client_order`，有单测）；② 跳板机下拉里选了会话却不勾
   「经跳板机」，等于**静默直连**。③ 顺带发现 e2e 假绿：「三跳」用例只读跳板机输入框、
   没验勾选框，实际一直在直连，跳板池从未参与——现已断言勾选、链顺序与两跳缓存。
   剩下的只是 AC-1 那条**真机 `ss` 观测**（见第 3 条）。
3. **证据强度不一**：`p0-coverage.md` 里标了哪些是 mock 侧证据、哪些有真机证据。
   尤其 `SES-024` 的 AC-1（`ss -tnp` 看到两条连接）目前**没有真机观测**。
4. **端到端偶发**：标签拖拽落点（已把落点从正中改到左四分之一）、CDP 合成拖拽
   偶发被吞（`Shift+Alt` 框选已加真实选区前提与重拖）、连跑多轮后 `local_open`
   偶发「打开失败」/ SSH 建连超时（失败点每轮漂移，重跑常能过）。**根因未完全定位**。
   2026-11-07 做过一次只读归因排查：一度怀疑「超时后游离会话 → conhost 累积 →
   正反馈成更多超时」，但逐 PID 核 conhost 归属后**否掉了这个因果**——当时 28 个
   conhost 中只有 7 个是孤儿，且启动时间全在 10-26 / 11-02，没有一个是当天 e2e 跑
   出来的；`cleanup()` 的 `taskkill /F /T /PID` 确实带走了每轮进程树，连跑时的
   「28→33」只是进程退出中的瞬时峰值、会自然回落，不是泄漏。
   **超时后回收迟到会话仍做、且保留**（防御性正确、无副作用）：`invokeWithTimeout`
   用裸 `Promise.race`，超时后底层 `invoke` 仍在跑、稍后可能注册一个前端已放弃的
   会话；现超时后继续盯底层 Promise，迟到成功且带 handle 就 `term_close` 回收，
   迟到失败静默丢弃（避免 unhandled rejection）。`scripts/check-late-session.mjs`
   从真源码抠函数、注入假 invoke 跑 5 场景，`check-docs.ps1` 9g 门禁盯着（做过删回收
   即红、还原即绿的变异验证）。**但别再把它写成「连跑偶发的根因」**——根因未定位，
   这条只是堵住一个理论上存在的资源缺口。
   首次建连超时仍保留「只对超时补点一次」。
   **`Ctrl+Tab` MRU 的「再按一次没切」已定位并修复**：那不是产品 bug，是验收用
   `__wt.tabs()` 的 `label` 当标签身份——本地 shell 起来后会用 OSC 2 标题把 label 改写
   （`本地 s14-18` → `pwsh.exe`），第二次按键时快照里的名字早已变了，判据自然不成立。
   现 `tabs()` 暴露稳定的 `view.id`，MRU 断言一律按 id 判定（点击目标也按 `dataset.id` 找），
   连跑两轮全绿。教训：**断言的身份要用稳定键，别用会被运行时改写的显示文本**。
5. **断言别只数 DOM 节点**（2026-11-08 两次踩到）：`SES-025` 的「三跳」只读跳板机输入框、
   没验「经跳板机」是否勾上；`TER-002` 的「左右分屏」只数 `.term-view` 节点、没验它可见——
   两条都因此长期假绿，而功能其实是坏的（三跳一直在直连、分屏右半边一直空白）。
   凡是「某块东西该出现在屏幕上」的断言，都要量 `getBoundingClientRect()` 的宽高，
   或读一个**由渲染结果推出**的状态，不要数节点、不要看类名。
   同理，**失败信息只写一句「超时」等于没写**：把当时实际的状态（面板开没开、焦点在哪、
   状态栏写的什么）一起报出来，否则下一轮还得重新猜——命令面板那条就是这么改的。
6. **本机环境**：连跑多轮后 `conhost`/`OpenConsole` 会变多（实测 32 个，其中 25 个属于
   **存活进程**）。**不要按名字批量杀**，会打断其它程序。
   另：**C 盘已满**（2026-11-08 实测可用 9.9 MB），`cargo fetch` 任何新依赖都会在解包阶段报
   `磁盘空间不足 (os error 112)`——本轮「命令面板」选零依赖实现就是因为它。要加依赖先腾 C 盘。
7. ~~`WT_SESSION=<id>` 未注入~~ **已做（本地终端）**：`local_open` 先定 ID、以 `WT_SESSION` 交给子进程，
   再用**同一个 ID** 注册句柄——两者相等，终端里的脚本能拿它和界面上的会话对上。e2e 两条断言：
   终端里读得到 UUID、且与 `window.__wt.handle` 完全一致（只验「非空」不够——环境变量与句柄是两条
   独立生成的路径，不一致就说明链断了）。远端 SSH 会话不注入：远端 shell 的环境由服务端决定，不伪造。
8. **SSH 压缩暂不开放**：`wt_ssh::SshConfig.compression` 字段在，但界面没有入口，`client::Config`
   一直用默认值（默认 `none` 排第一，等于不压）。2026-11-08 试过接上 `russh` 的
   `Preferred.compression`（顺序 `zlib@openssh.com` → `zlib` → `none`）：配置层单测通过，
   但**开启压缩后 e2e 的连接建不起来**。**根因未定位**——可能是 russh 客户端压缩实现的问题，
   也可能是应用内 mock 服务端不支持该方向压缩。没有真机 `sshd` 对照前不开放这个开关：
   一个「打开就连不上」的开关比没有更糟。要再动它，先准备一台真 sshd（`sshd_config` 里
   `Compression yes`）做对照实验，确认是客户端还是 mock 的问题。
