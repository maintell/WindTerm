# 第一册 · 产品规格说明书 · 索引

## 本册要解决的问题

MobaXterm 的功能表面上是「一个带标签页的 SSH 客户端」，实际上它是一套**远程运维工作台**：连接管理、终端仿真、文件传输、远程桌面、网络诊断、本地 POSIX 环境、凭据保险库、扩展机制，八件事被塞进同一个进程里，互相之间的衔接（比如「在终端里 cd 到某目录，左侧文件浏览器跟着走」）才是它真正的粘性来源。

所以本册不是「功能列表」，而是三件东西：

1. **一份可核对的基线**——`04-feature-matrix.md` 把 MobaXterm 官网列出的每一项能力和帮助文档里的每一个配置项都编号，逐条给出「做 / 不做 / 换个做法」的结论。任何「这个功能要不要做」的争论，先看矩阵。
2. **一套可验收的规格**——每个模块的规格都写清楚交互流程、状态机、异常分支、配置项和验收标准。验收标准必须是**可执行的**（能写出测试用例），不接受「体验良好」这种描述。
3. **一条可交付的路径**——`14-roadmap-acceptance.md` 把需求切成里程碑，每个里程碑有明确的退出条件。不排期的需求不算需求。

## 三条贯穿全册的硬约束

写任何一条规格时都不能违反，违反即视为规格缺陷：

**① 不得要求用户为了用 WindTerm 而改变服务器。**
MobaXterm 的很多能力依赖服务端配合（Mosh 需要 `mosh-server`、SFTP 浏览器在 `Keyboard-interactive` 认证下会重复要密码、跳板机需要 `AllowTcpForwarding`）。WindTerm 必须在**服务端零改动**的前提下尽量工作；确实做不到的（如 Mosh），必须在规格中显式写出「服务端前置条件」并给出不依赖它的替代路径。

**② 不得把「配置」当成「功能」。**
每一个配置项都必须能回答：不配置时默认行为是什么？配置后改变的是哪条代码路径？如果一个选项只是把某个常量换个值，那它是实现细节，不该出现在 UI 上。MobaXterm 的设置项有相当一部分属于此类（例如 Xorg 版本选择），我们在矩阵中标注 `ALT` 并说明为什么不照搬。

**③ 不得留下「只能靠文档才能用对」的路径。**
凡是需要用户理解内部机制才能正确使用的功能（典型：多跳跳板机 + SFTP 浏览器的叠加、SSH 密钥权限、编码错乱），必须在 UI 上给出**当场可读的解释与修复动作**，而不是让用户去翻帮助文档。这条直接来自 MobaXterm 帮助文档里大量「FAQ 式排错」——那些 FAQ 的存在本身就说明原设计的可发现性不足。

## 与第二册的对应关系

每个 `spec/` 文档末尾有「设计映射」表，指向实现它的 `design/` 章节。反向地，`design/` 每个文档开头声明它实现了哪些需求 ID。
这条双向链接是强制的：**没有需求来源的设计是过度设计，没有设计承接的需求是空话。**
