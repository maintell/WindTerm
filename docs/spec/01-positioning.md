# 01 · 产品定位与范围

## 1. 问题定义

### 1.1 一个运维工程师的真实工作台长什么样

一个典型的 Linux 运维/后端工程师，一天之内要在同一台机器上反复切换这些动作：

```
看日志     → SSH 连到跳板机，再跳到业务机，tail -f /var/log/app.log
改配置     → 想直接编辑远端 nginx.conf，不想 vim
传文件     → 把本地构建产物 scp 上去，再拉回一份日志
看图       → 远端生成的监控图、截图，要能在本地看
连桌面     → 有一台 Windows 服务器只能 RDP，要传个文件上去
连 Windows → 有一台 Windows 服务器只能 RDP
开隧道     → 本地 3306 连不上，要 -L 转发
查网络     → 端口通不通、谁在监听、抓个包
管凭据     → 20 台机器、3 套密钥、1 个主密码
```

这八件事**任何单独一件都有成熟工具**：OpenSSH、WinSCP、VS Code Remote、MobaXterm、Remmina、PuTTY、DBeaver……
痛点不在「有没有」，而在**上下文切换成本**：每换一个工具就要重新找主机、重新认证、重新定位路径，而且它们之间不共享状态。

MobaXterm 的价值就是把这八件事压进一个进程、一份配置、一次认证。它的粘性不来自任何单点功能强，而来自**衔接**：

- 终端 `cd /var/log` → 左侧 SFTP 浏览器自动跟到同一目录（"Follow SSH path"）
- 双击远端文件 → 内嵌编辑器打开 → `Ctrl+S` 直接写回远端
- SSH 连上 → DISPLAY 自动设好 → 远端 `xclock` 直接在本地弹出
- 同一份会话配置 → 既能开终端也能开 RDP

**WindTerm 要复制的是这套衔接，而不是功能条目本身。** 这也是为什么本项目的验收标准是「端到端任务流能跑通」，而不是「功能勾选表打满」。

### 1.2 为什么现有方案不够

三个结构性问题，任何单点补强都解决不了：

**① 平台锁定。** MobaXterm 只有 Windows 版。而现代研发团队是混合的：后端用 macOS、运维用 Windows、CI 与跳板机是 Linux。一个团队被迫维护两套工具链和两套配置。
**② 不可审计。** 运维工具天然持有最高权限凭据（生产 root、跳板机密钥、RDP 管理员）。闭源二进制无法回答「它把我的密码存在哪、用什么算法、会不会外发」。企业安全评审经常因此直接否掉。
**③ 不可扩展。** MobaXterm 的插件机制本质是「往 zip 里塞二进制放到 `/bin`」，没有权限模型、没有签名、没有版本约束。想加一个内部工具，只能靠人肉分发。

### 1.3 我们要解决的核心矛盾

> **能力广度 vs 可信度。**
> 功能越全的工具，攻击面越大、越难审计；越安全的工具，越难用。

我们的答案是：**把「广度」和「可信」拆到不同层次解决**——
- 广度靠**协议栈自己实现**（Rust，内存安全，可审计）；
- 高风险/重资产能力（抓包驱动、完整 POSIX 环境）做成**可选、外部、可替换的 provider**，主程序不背这个包袱；
- 所有跨边界的动作（凭据读取、外部进程启动、网络出站）都有**显式权限与审计记录**。

这条原则直接决定了后面所有架构决策（见 ADR-0001、ADR-0002、ADR-0007）。

## 2. 竞品全景

### 2.1 分类

市面上的工具可以按「覆盖了几件事」分成四层：

| 层 | 覆盖 | 代表 | 特征 |
|---|---|---|---|
| L1 单协议客户端 | 1 件事 | PuTTY、WinSCP、VcXsrv、TightVNC | 免费/开源、极简、零整合 |
| L2 终端工作台 | 终端 + 文件传输 | Xshell+Xftp、SecureCRT、Tabby、Electerm、FinalShell、WindTerm(kingToolbox) | 终端体验好，无图形转发、无 RDP |
| L3 远程桌面聚合器 | 多协议连接 | mRemoteNG、Royal TS、Remmina、Termius | 协议多，终端弱，整合度中等 |
| L4 一体化工作台 | 终端 + 文件 + 图形 + 桌面 + 工具集 | **MobaXterm** | 唯一一个把八件事都做了的 |

**空位很清楚：L4 只有一个玩家，且它只在 Windows 上、且闭源。**

### 2.2 逐项对照

| 产品 | 平台 | 许可 | SSH | SFTP | X11 转发 | RDP | VNC | 串口 | 本地 POSIX 环境 | 会话同步 |
|---|---|---|---|---|---|---|---|---|---|---|
| **MobaXterm** | Win | 闭源 | ✅ | ✅ | ✅ 内置 X Server | ✅ | ✅ | ✅ | ✅ Cygwin | 共享文件夹 |
| SecureCRT | Win/mac/Linux | 商业 | ✅ | ✅ | ❌ | ❌ | ❌ | ✅ | ❌ | 手动 |
| Xshell + Xftp | Win | 商业（家用免费） | ✅ | ✅ | ❌ | ❌ | ❌ | ✅ | ❌ | 手动 |
| Tabby | 三平台 | MIT | ✅ | ✅ | ❌ | ❌ | ❌ | ✅ | ❌ | 插件/自建 |
| WindTerm (kingToolbox) | 三平台 | 开源 | ✅ | ✅ | ❌ | ❌ | ❌ | ✅ | ❌ | ❌ |
| Termius | 三平台 | 商业 | ✅ | ✅ | ❌ | ❌ | ❌ | ❌ | ❌ | 云 |
| Remmina | Linux | GPL | ✅ | ✅ | 部分 | ✅ | ✅ | ❌ | ✅ 原生 | ❌ |
| mRemoteNG | Win | GPL | ✅ | ❌ | ❌ | ✅ | ✅ | ❌ | ❌ | ❌ |
| Royal TS | 三平台 | 商业 | ✅ | ✅ | ❌ | ✅ | ✅ | ✅ | ❌ | 商业云 |
| FinalShell | 三平台 | 闭源免费 | ✅ | ✅ | ❌ | ❌ | ❌ | ❌ | ❌ | 云 |

> 表中「X11 转发」指**客户端自带可用的 X Server 或完整的转发链路**。仅支持 `ssh -X` 但没有本地 X Server 的，记为 ❌（用户仍需自己装 X Server，体验不成立）。
>
> **WindTerm 在本表中位于「X11 转发 ❌」一列**——这是刻意的取舍，不是能力缺口。理由见 §3.2 与 ADR-0012：X11 的体验上限由第三方 X Server 决定，我们无法承诺质量，因此选择不做，并把替代路径（自装 X Server + 系统 `ssh -X`）写进文档。
> 此表为 2026-11 基于各产品公开文档的归纳，实施前需按 `appendix/c-references.md` 复核一次。

### 2.3 我们的位置

```
                 协议广度 →
       窄                                  宽
     ┌──────────────────────────────────────────┐
  高 │  Tabby        Xshell          MobaXterm  │
     │  WindTerm(k)  SecureCRT       ★ 我们要去的格子
  整 │  Termius                       (跨平台+开源+同等广度)
  合 │  FinalShell                              │
  度 │  ─────────────────────────────────────── │
     │  PuTTY   WinSCP   Remmina    mRemoteNG   │
  低 │  VcXsrv           Royal TS               │
     └──────────────────────────────────────────┘
```

**一句话定位：**

> WindTerm 是唯一一个**跨平台、开源、把终端、文件传输、RDP/VNC 与会话治理做成一体的远程运维工作台**——它把 MobaXterm 的核心能力集合搬到三大平台（X11 转发除外，见 §3.2），并把凭据、配置、扩展三件事做成可审计、可脚本化、可被企业策略约束的形态。

### 2.4 差异化的三个支点

不做「MobaXterm 的克隆」，因为克隆永远只是追赶。三个必须自己走出来的支点：

**支点一：跨平台不是「也能跑」，而是「同一份配置在三平台行为一致」。**
会话、快捷键、配色、宏、插件包跨平台通用；只有真正与 OS 相关的部分（凭据后端、串口驱动）做适配层。这一点 MobaXterm 结构上做不到。

**支点二：可脚本化。**
MobaXterm 的自动化止步于宏录制与命令行开关。WindTerm 要求：**每一个 UI 能做的事，都能用一条 CLI 命令做完，并且输出机器可读结果**（`--json`）。
这让它可以直接嵌进 CI、跳板机自动化、批量巡检脚本。这既是用户价值（运维脚本化），也是我们自己的质量保障手段（E2E 测试直接驱动 CLI）。

**支点三：可审计的安全模型。**
凭据存储格式公开、加密参数公开、所有出站连接与外部进程启动可记录、企业可用策略文件关闭高风险能力。
这一条决定了能不能进企业，而企业是这类工具唯一愿意付费/愿意推动内部采纳的场景。

## 3. 范围

### 3.1 范围内（In Scope）

| 域 | 内容 |
|---|---|
| 连接 | SSH（含跳板机、代理、多跳）、Telnet、Rlogin/Rsh、Mosh、串口、本地终端 |
| 终端 | VT100/xterm 兼容仿真、标签、分屏、多执行、搜索、语法高亮、日志、宏 |
| 文件 | SFTP/SCP/FTP/FTPS 客户端、图形文件浏览器、传输队列、内嵌编辑器、Diff、图片查看 |
| 图形 | RDP、VNC、图形会话截图（**不含 X11 转发 / X Server / XDMCP**，见 §3.2） |
| 网络 | 本地/远程/动态端口转发、图形隧道管理、内置服务端（HTTP/FTP/SSH/TFTP/Telnet）、端口诊断、抓包（外部依赖） |
| 本地 | 本地终端、POSIX 路径命名空间（`/drives`、`//host/share`）、内置工具集、密钥生成器 |
| 平台 | 会话模型与持久化、导入导出与迁移、设置体系、主题与快捷键、插件与包管理、CLI 与协议处理、系统托盘、自动更新 |
| 安全 | 主密码、加密保险库、密钥格式兼容、主机密钥校验、审计日志、企业策略 |

### 3.2 范围外（Out of Scope）——反目标

明确写下不做的事，比写下要做的事更能防止项目失控：

| 不做 | 理由 |
|---|---|
| **通用远程桌面/远程控制**（AnyDesk、Parsec、TeamViewer 那类） | 需要 NAT 穿透、中继基础设施、屏幕编解码优化，是完全不同的产品。我们只做「已知地址的 RDP/VNC 连接」 |
| **云同步服务端** | 我们不运营用户数据。同步只支持用户自建的共享目录 / HTTP / SFTP / WebDAV，见 `SES-019` |
| **密码管理器**（浏览器插件、移动端、自动填充网页） | 凭据保险库只为「连接认证」服务，不做通用密码管理 |
| **IDE** | 内嵌编辑器定位是「改远端配置、看日志」，不追 LSP、调试器、Git 图形化 |
| **Kubernetes / 容器 / 云资源管理面板** | 属于上层编排工具，不与本产品竞争。只提供「连到那台机器」的能力 |
| **自带完整 POSIX 环境**（不打包 Cygwin/MSYS2） | 见 ADR-0003。改为「内置 Rust 工具集 + 可选 MSYS2 桥接 + 优先复用 WSL」 |
| **X11 转发 / X Server 集成 / XDMCP** | 见 ADR-0012。X11 必须依赖本地 X Server（Windows 装 VcXsrv、macOS 装 XQuartz），与「跨平台、开箱即用、零外部依赖」冲突；且体验质量由第三方 X Server 决定，我们无法保证。用户仍可用系统 `ssh -X` + 自装 X Server |
| **移动端 App** | 三平台桌面已覆盖目标场景；移动端 RDP/SSH 是另一个产品形态 |
| **浏览器版** | WebView 已是我们前端；再做一个纯 Web 版会把安全模型摊平（浏览器不能持有长期凭据） |
| **遥测、崩溃上报、使用统计** | 默认零外发。崩溃诊断只在用户主动导出时生成文件 |

### 3.3 边界判定规则

遇到「这个要不要做」的争议，按顺序问三个问题，任一为「是」就出局：

1. **它是否要求我们运营服务器或持有用户数据？** → 出局（违反离线优先）
2. **它是否只有在用户放弃现有工具链的情况下才有价值？** → 出局（我们要做的是整合，不是替换生态）
3. **去掉它之后，MobaXterm 用户的核心任务流是否仍然完整？** → 若「是」，降级为 P2/P3 而非 P0/P1

## 5. 许可与合规

这是硬约束，必须在写第一行代码前定下来，否则后期无法回退。

### 5.1 自有代码：Apache-2.0

选择理由：
- 专利授权条款（§3）对协议实现类项目重要——RDP/SSH 相关专利风险需要明确的授权姿态；
- 与 GPL 兼容（可被 GPL 项目引用），但不会强制下游开源，利于企业内部采用与二次分发；
- 与 Rust 生态主流一致。

### 5.2 第三方组件分类

| 类别 | 组件 | 许可 | 分发策略 |
|---|---|---|---|
| 可随包分发 | Rust crates（russh、IronRDP、rusqlite、tokio…） | MIT / Apache-2.0 / BSD | 随主包，生成 `THIRD-PARTY-NOTICES` |
| 可随包分发 | `uutils/coreutils`（内置工具集） | MIT | 随主包（独立进程） |
| 可随包分发 | OpenH264（RDP EGFX 解码） | BSD + Cisco 专利授权 | 随主包，**必须**使用 Cisco 提供的二进制以获得免费专利授权，不得自行编译 |
| **不可随主包分发** | MSYS2 运行时 | GPL-3.0 等 | 用户自装，我们只做检测与桥接 |
| **不可随主包分发** | Npcap（抓包驱动） | 专有（免费版限制再分发） | 用户自装，我们只做检测与引导 |

> **X11 相关组件（VcXsrv / Cygwin-X / XQuartz / Xorg）已不在依赖清单内**——X11 能力整体移除（ADR-0012），
> 主包因此少了一个 GPL 依赖，也少了一个「首次使用需额外安装」的断点。
### 5.3 专利风险

| 风险点 | 说明 | 缓解 |
|---|---|---|
| RDP 的 EGFX/H.264 | H.264 解码涉及 MPEG-LA 专利池 | 只使用 OpenH264 官方二进制（Cisco 承担专利费），或退回 RemoteFX/NSCODE 编码；在设置中标注该选项的许可来源 |
| RDP 协议本身 | 微软 RDP 协议文档公开（MS-RDPBCGR 等），实现自由 | 只依据公开规范实现，不参考微软私有实现 |
| VNC 的 Tight/ZRLE 编码 | TightVNC 编码曾有争议 | 优先 RFB 标准编码（Raw/CopyRect/Hextile/ZRLE/RRE），Tight 作为可选并注明来源 |
| SSH 加密算法 | 算法本身无专利问题 | 只启用现代算法集，禁用已被攻破的（见 `SEC-005`） |

### 5.4 商标与命名风险 ⚠️

**存在一个必须现在解决、后期改名代价极大的问题：**

GitHub 上已有 `kingToolbox/WindTerm` —— 一个开源的 SSH/SFTP/串口终端，与本项目**同名且同赛道**。后果：
- 用户搜索 "WindTerm" 会先找到它，我们无法建立搜索可见性；
- 包管理器（Homebrew / winget / apt / AUR）的包名会被占用或冲突；
- 若未来商业化，商标无法注册。

**建议（需产品决策，见 ADR-0011）：**
- 保留 `WindTerm` 作为**内部代号 / 仓库名**不变（用户已定）；
- **对外发布名**改用可注册的独立名称，候选：`WindPort`、`WindStation`、`GaleTerm`、`Zephyr`（需做商标检索）；
- 二进制名、包名、协议 scheme（`windterm://`）、配置目录名从一开始就与对外名一致，避免二次迁移。

> 在 ADR-0011 决议前，所有文档统一使用 `WindTerm` 作为**代号**，代码中的 crate 前缀统一用 `wt-`（与最终名解耦）。

## 6. 产品原则

五条，用于裁决后续所有设计分歧：

1. **衔接优先于功能。** 新增一个孤立功能的价值，低于把两个已有功能连起来。
2. **默认安全，显式放开。** 危险能力（开放 0.0.0.0 监听、禁用主机校验、保存明文密码）默认关闭，开启时必须解释后果。
3. **可解释的失败。** 任何错误都必须回答三件事：发生了什么、为什么、我该点哪里。禁止只抛协议层原文。
4. **不绑架用户数据。** 配置与凭据格式公开、可导出、可迁移；卸载不损坏数据；不锁定到我们的服务。
5. **离线是一等公民。** 所有功能在无网络（除目标主机可达）时可用；不联网也能启动、不能因联网失败而降级。
