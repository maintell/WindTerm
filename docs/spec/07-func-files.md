# 07 · 功能规格 · 文件传输与编辑

承接需求：`FIL-001`~`FIL-023`

## 1. 范围与设计立场

文件传输在 MobaXterm 里是「SSH 会话的附属物」：连上 SSH 就弹出侧栏浏览器，双击文件用内嵌编辑器改。
这个设计很聪明，但它有三个没做完的地方：

1. **没有传输队列**——大文件传一半失败，只能重来；
2. **编辑器是玩具**——没有编码/换行符控制，改 GBK 文件会乱码，改完保存可能把 CRLF 变 LF；
3. **「跟随路径」是实验特性**——需要往远端 shell 注入钩子，在 zsh/fish 下经常失效。

我们的规格在这三点上必须明确优于它，其余保持行为一致（`C1`）。

### FIL-002 · SFTP 协议

| 字段 | 值 |
|---|---|
| 优先级 | P0 · 兼容性 C1 |

**协议版本**：SFTP v3（OpenSSH 事实标准）。v4/v5/v6 不实现（无主流服务端使用）。

**必须正确处理的点**

| 点 | 要求 |
|---|---|
| 并发请求窗口 | 默认 64 个在途请求，可调 1~128；影响小文件吞吐 |
| 大文件 | 使用 `u64` 偏移，支持 > 4 GB；单次读写 32 KB~256 KB 自适应 |
| 符号链接 | `SSH_FXP_SYMLINK` 参数顺序在不同服务端实现不一致（OpenSSH 与其他），需探测兼容 |
| 权限 | `SSH_FXP_SETSTAT` 设置 mode/uid/gid/mtime |
| 硬链接 | `SSH_FXP_EXTENDED hardlink@openssh.com`（可选） |
| 扩展 | `posix-rename@openssh.com`（原子重命名，保存文件时必需）、`statvfs@openssh.com`（可用空间）、`fsync@openssh.com` |
| 错误映射 | SFTP 状态码 → 可读消息（`SSH_FX_PERMISSION_DENIED` → 「权限不足」并显示所需权限） |

**关键约束**：保存远端文件时**必须**用 `posix-rename@openssh.com` 做原子替换；服务端不支持时降级为「先删后改名」并提示存在短暂不一致窗口。

**验收标准**

- [ ] AC-1 上传 6 GB 文件成功，进度准确，内存占用不随文件大小增长
- [ ] AC-2 与 OpenSSH 7.4 / 8.0 / 9.x、Dropbear、ProFTPD mod_sftp 五种服务端互通
- [ ] AC-3 保存文件时服务端 `inotifywait` 只观察到一次 `MOVED_TO`，无中间态空文件
- [ ] AC-4 目录含 5000 个文件时列表在 2 s 内返回（并发窗口生效）

### FIL-003 · SCP 协议

| 字段 | 值 |
|---|---|
| 优先级 | P1 · 兼容性 C1 |

**决策**：只做一套实现 + 兼容检测，不做 MobaXterm 的「enhanced / normal」双实现。

| 场景 | 行为 |
|---|---|
| 服务端 OpenSSH ≥ 9.0 | 使用 `scp -O` 等价路径（走 SFTP 后端），速度最优 |
| 服务端 OpenSSH < 9.0 | 使用 legacy SCP 协议（`\x01` 确认 + 文件名行协议） |
| 自动检测 | 连接后执行 `scp -V` 或探测 `subsystem sftp` 可用性来决定 |

**为什么不做双实现**：MobaXterm 的「enhanced speed」与「normal speed」是两套独立代码路径，行为差异导致过用户困惑（同一操作在不同设置下结果不同）。我们的检测是自动的，用户不需要理解。

**验收标准**

- [ ] AC-1 对 OpenSSH 8.0 与 9.6 分别上传 100 MB，均成功且速度差异 < 15%
- [ ] AC-2 文件名含空格、中文、`$`、换行时正确转义

### FIL-005 · 双击编辑远端文件

| 字段 | 值 |
|---|---|
| 优先级 | P0 · 兼容性 C1 |
| 来源 | `F:text-editor` `D:1.6` |

**流程**

```
双击 → 检查大小/类型 → 下载到临时区 → 记录 (mtime, size, mode, uid, gid)
     → 编辑器打开 → 用户修改 → Ctrl+S
     → 检查远端是否被他人修改（mtime/size 变化）
     → 写临时文件 + fsync + posix-rename → 恢复 mode/owner
     → 提示「已保存到 user@host:/path」
```

**规则**

| 情况 | 行为 |
|---|---|
| 文件 > 20 MB | 拒绝打开，提示「文件过大，请下载后编辑或使用远端 vim」，提供「仍要打开」 |
| 检测到 NUL 字节 | 判定为二进制，拒绝文本编辑，提示「用图片查看器/下载」 |
| 无写权限 | **打开时**即提示「你没有写权限，保存将失败」，提供「以 sudo 保存」（见下） |
| 编辑期间远端变更 | 保存时提示「远端文件已被修改」，展示 diff，提供「覆盖 / 放弃 / 另存为」 |
| 连接断开 | 保留编辑内容，状态栏显示「未保存（连接断开）」，支持重连后重试 |
| 保存失败（磁盘满） | 保留未保存状态，显示远端 `statvfs` 的可用空间 |

**「以 sudo 保存」**：通过 `sudo tee` 写临时文件再 `sudo mv`，需要用户在终端里输入 sudo 密码或已配置 NOPASSWD。实现时**不缓存 sudo 密码**。

**验收标准**

- [ ] AC-1 编辑 100 KB 文件，从双击到可编辑 ≤ 1.5 s
- [ ] AC-2 保存后 `stat` 显示 mode/uid/gid 未变，mtime 更新
- [ ] AC-3 编辑期间用另一终端 `echo x >> file`，保存时提示冲突并展示 diff
- [ ] AC-4 断开网络后保存，内容保留且可重连后重试成功

### FIL-016 · rsync 增量同步

| 字段 | 值 |
|---|---|
| 优先级 | P2 · 兼容性 **C3** |

**决策**：不内置 rsync 二进制。

| 场景 | 行为 |
|---|---|
| 远端有 `rsync` | 通过 SSH 执行远端 `rsync`（`--server` 模式），本地作为客户端。**需要本地也有 rsync** → 若本地没有，改用方案 B |
| 本地/远端任一缺 rsync | 退回「SFTP 增量」：按 `size + mtime` 比对，只传变化的文件；不支持块级差分 |

**UI**：一个「同步」对话框：源、目标、方向（单向/双向）、排除规则（glob）、删除多余文件（危险，需确认）、预演（dry-run 显示将要做什么）。

**诚实说明**：块级差分（rsync 的核心优势）只在双方都有 rsync 时可用。UI 必须显示当前使用的模式，不能让用户以为「总是块级差分」。

### FIL-017 · 跟随终端路径

| 字段 | 值 |
|---|---|
| 优先级 | P2 · 兼容性 C1 |

**问题**：MobaXterm 的实现是「实验性」的，需要往远端 shell 注入钩子，在 zsh/fish/自定义 PS1 下经常失效，且会污染用户环境。

**我们的方案（三级降级）**

| 级别 | 机制 | 前提 |
|---|---|---|
| L1 最优 | 解析终端 `OSC 7`（`\e]7;file://host/path\e\\`） | 远端 shell 已配置（许多发行版默认开启，如 Ubuntu 的 bash 配置） |
| L2 兜底 | 解析输入行中的 `cd <path>` 并在本地维护一个「推测的当前目录」 | 用户手动 `cd`；不准确时以 L1 为准 |
| L3 手动 | 工具栏「同步到终端目录」按钮 | 总是可用 |

**不做的事**：不注入 shell 钩子、不修改远端 `.bashrc`、不执行隐藏命令去查询 `pwd`（会污染历史与审计日志）。

**行为**：L1 命中时侧栏自动跳转（可关）；L2 命中时侧栏显示一个「可能已切换到 /x/y，是否同步？」的可点击提示（不自动跳，避免误判）。

### FIL-018 · 元数据保留

| 项 | 上传 | 下载 |
|---|---|---|
| mtime | 保留源文件 mtime（`SETSTAT`） | 保留远端 mtime |
| 权限 | 策略：保留源 / 统一为 644 / 询问 | 保留远端 mode（尽力） |

### FIL-019 · 大文件与断点续传

- 支持 > 4 GB（`u64` 偏移）。
- 断点续传：
  - 下载：比较本地已有文件大小与远端大小，从 `size` 处 `FXP_READ` 续传。
  - 上传：比较远端已有文件大小，从 `size` 处 `FXP_WRITE` 续传（要求服务端支持 `append` 语义，通过 `SSH_FXF_APPEND` 或不带 `TRUNC` 的 `WRITE`）。
- 续传前校验：比较前 N KB 的哈希（可配，默认 64 KB），不一致则从头传（避免文件已变更）。
- 进度：按字节，显示速度与剩余时间；每 500 ms 更新一次（避免 UI 抖动）。

### FIL-020 · ZMODEM

- 检测终端输出中的 ZMODEM 头（`**\x18B00` 等）。
- 检测到 `rz`（远端请求接收）→ 弹出文件选择 → 通过终端通道发送。
- 检测到 `sz`（远端发送）→ 弹出保存位置 → 接收。
- 支持 ZMODEM-8K、崩溃恢复（`ZCRSE`）、32 位 CRC。
- 传输期间终端显示进度条（覆盖在终端底部，不污染缓冲）。

### FIL-021 · 本地文件管理

双栏中的本地侧提供：新建文件夹/文件、重命名、删除（到回收站）、复制/剪切/粘贴、用系统程序打开、在资源管理器中显示、属性。不实现压缩/解压（交给系统工具）。

### FIL-022 · 传输限速与并发

- 全局限速（KB/s 或 MB/s）、单任务限速。
- 令牌桶实现，允许短时突发。
- 用途：避免 SFTP 占满上行导致终端输入卡顿。
- 提供「智能限速」：检测到终端交互时自动降速（P2）。

### FIL-023 · 完整性校验

- 传输完成后可选校验：本地算 SHA-256，远端执行 `sha256sum <file>`（若无该命令则降级 `md5sum`，都无则跳过并提示）。
- 结果：一致/不一致/无法校验；不一致时提供「重新传输」。
- 默认关闭（大文件校验耗时），可配「> 100 MB 时自动校验」。

## 3. 传输引擎规格

### 3.1 状态机

```
        ┌──────────┐
        │  Queued  │
        └────┬─────┘
             │ 调度
        ┌────▼─────┐   暂停   ┌────────┐
        │ Running  ├─────────►│ Paused │
        └────┬─────┘◄─────────└────────┘
             │ 完成/失败/取消
     ┌───────┼────────┐
     ▼       ▼        ▼
┌─────────┐┌────────┐┌──────────┐
│Completed││ Failed ││ Canceled │
└─────────┘└───┬────┘└──────────┘
               │ 重试
               └──► Queued
```

### 3.2 分块与并发

| 参数 | 默认 | 说明 |
|---|---|---|
| 块大小 | 128 KB | 小文件降为 32 KB，大文件升为 256 KB |
| 在途块数 | 8 | 受 SFTP 窗口（64）约束 |
| 单文件并发 | 1 | 多块顺序写（SFTP 不支持乱序写同一文件） |
| 多文件并发 | 4 | 全局 |

> 注意：SFTP 的 `WRITE` 必须按偏移顺序提交才能保证语义；并发只用于**多个文件之间**，不用于单文件内。这是与 HTTP 分块上传的关键差异。

### 3.3 错误分类与重试

| 类别 | 例子 | 重试 |
|---|---|---|
| 瞬时 | 连接超时、`SSH_FX_FAILURE` 偶发 | 自动重试 3 次，指数退避 |
| 权限 | `SSH_FX_PERMISSION_DENIED` | 不重试，提示 |
| 空间 | `SSH_FX_NO_SPACE_ON_FILESYSTEM` | 不重试，显示可用空间 |
| 路径 | `SSH_FX_NO_SUCH_FILE` | 不重试，提示创建目录 |
| 协议 | 未知状态码 | 不重试，记录诊断信息 |
