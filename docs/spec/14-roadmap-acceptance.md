# 14 · 版本路线图与验收

## 1. 里程碑总览

| 里程碑 | 目标 | 范围 | 退出条件（摘要） |
|---|---|---|---|
| **M0 · 技术验证** | 证明关键技术可行，消除所有 `【待验证】` | 8 个技术 spike | 每个 spike 有书面结论 + 可运行的原型代码 |
| **M1 · MVP** | 能替代 MobaXterm 完成核心工作流 | 44 条 P0 | FLOW-1/2/3 通过；`NFR-001/002/003` 达标 |
| **M2 · v1.0** | 能力对齐 MobaXterm 的核心集合 | 累计 125 条（P0+P1） | FLOW-1~6 全通过；MobaXterm 迁移验收通过 |
| **M3 · v1.x** | 补齐增强项 | 累计 187 条（+P2） | 无 P0/P1 缺陷；性能无回归 |
| **M4 · v2.0** | 结构性演进 | 架构级改造 | 见 §6 |

**为什么先有 M0 而不是直接做 M1**：本项目的两个最大风险（Tauri 二进制 IPC 性能、RDP 集成度）都无法靠读文档消除。用 2~4 周做验证，比用 6 个月做一个不可用的产品便宜得多。X11 能力移除后（ADR-0012），原先的第三大风险（X11 中文输入法）一并消失。

## 2. M0 · 技术验证

### 2.1 验证清单

每个 spike 必须有：**结论（可行/不可行/有条件可行）、实测数据、对规格的修订、原型代码位置**。

| # | 验证项 | 关键问题 | 通过标准 | 失败后的应对 |
|---|---|---|---|---|
| **S1** | Tauri 2 二进制 IPC | 终端数据能否以原始字节零拷贝传输？延迟与吞吐如何？ | 单次往返 ≤ 1 ms；连续传输 ≥ 50 MB/s；`ArrayBuffer` 直通无需 base64 | 改用本地 WebSocket；再不行改共享内存 + 环形缓冲 |
| **S2** | xterm.js 吞吐 | 20 MB/s 持续输出下是否丢字节、UI 是否可交互？ | `NFR-003` 达标；60 s 压测无卡死 | 启用 Rust 终端内核备选方案（ADR-0004） |
| **S3** | IronRDP 集成度 | NLA/EGFX/剪贴板/驱动器重定向是否可用？帧率？ | 4 项能力全通；1080p ≥ 25 fps | 降级：EGFX 关闭用 RemoteFX；驱动器重定向推迟 |
| **S4** | russh 的转发与 agent 能力 | `direct-tcpip`、`tcpip-forward`、agent 转发是否完备？ | 跳板机、`-R`、agent 转发三项全部跑通 | 换 `ssh2`（libssh2）或自行补实现 |
| **S5** | 终端中文与 emoji 渲染 | CJK 列宽、组合字符、emoji ZWJ、输入法组合在 xterm.js 下是否全部正确？ | `TER-025` AC-1~4 全通过；vim/top 不错位 | 调整列宽策略或启用 Rust 终端内核（ADR-0004 备选） |
| **S6** | MobaXterm ini 解析 | 真实 ini 的字段名与协议枚举是什么？加密密码能否解密？ | 3 个版本样本解析成功；字段映射表完成；解密结论明确 | 放弃解密，只做「凭据补录向导」（`spec/05` §5.4） |
| **S7** | 保险库格式 | Argon2id + XChaCha20-Poly1305 的独立实现能否解密？解锁耗时？ | Python 独立实现解密成功；解锁 ≤ 500 ms | 调整 KDF 参数（降 m 到 32 MiB） |
| **S8** | 跨平台 WebView 一致性 | WebKitGTK 上终端渲染/输入/字体是否与 Windows 一致？ | 三个平台截图差异 ≤ 2%；输入法可用 | Linux 限定支持发行版；必要时用 CEF |

### 3.3 内部依赖顺序

P0 需求之间存在硬依赖，必须按序实现：

```
① 基础层：配置存储(SET-006) → 保险库(SEC-007) → 主密码(SEC-001)
                ↓
② 会话层：会话模型 → SSH(SES-001) → 主机密钥(SEC-005) → 密钥格式(SEC-003)
                ↓
③ 终端层：PTY/通道 → 终端渲染(TER-001/005/006/008/011) → 流控(TER-034)
                ↓
④ 复用层：SFTP(FIL-002) → 浏览器(FIL-001/004/005/011)
          跳板机(SES-024) → 隧道(NET-001/004)
                ↓
⑤ 图形层：RDP 客户端(GUI-015) → 剪贴板(GUI-018) → NLA(GUI-022)
          RDP(GUI-015/018/022)
                ↓
⑥ 体验层：多标签(TER-001) → 多执行(TER-004) → 快捷键(TER-020)
                ↓
⑦ 迁移与发布：导入(SES-020/SET-013) → 打包(SYS-008)
```

**关键路径**：`SET-006 → SEC-007 → SES-001 → FIL-002 → GUI-015`。任何一环延期都直接推迟 MVP。

## 6. M4 · v2.0（结构性演进）

不在本次规格的交付范围内，只登记方向，避免 M1~M3 的设计堵死它们：

| 方向 | 前提 | 影响的设计决策 |
|---|---|---|
| Rust 终端内核替换 xterm.js | `NFR-003` 在 M3 成为瓶颈 | 必须保留 `TerminalBackend` trait（`design/03` §1） |
| 会话云同步（自建服务端） | 用户需求明确 | 数据模型需支持「变更集」（`design/04` §3 已预留 `updatedAt`/`rev`） |
| 团队协作（共享终端会话） | — | 终端数据流需可多路复用（`design/02` §4 已按多订阅者设计） |
| 移动端只读查看 | — | 核心与 UI 已分离（`design/01` §3） |

## 7. 迁移验收（M2 必过）

这是产品能否被采用的唯一硬门槛，必须像功能验收一样严格执行。

### 7.1 验收环境

招募 5 名真实 MobaXterm 用户（≥ 2 年使用史），提供其真实 `MobaXterm.ini`（脱敏后），在他们的真实工作机上执行。

### 7.2 验收项

| # | 项 | 通过标准 |
|---|---|---|
| A1 | 导入完整性 | 会话数、文件夹层级、名称、协议类型 100% 一致 |
| A2 | 导入可用性 | 随机抽 10 个会话，双击后 10 个都能连上（凭据已补录） |
| A3 | 视觉一致性 | 终端字体、字号、配色与 MobaXterm 的差异被用户判定为「可接受」 |
| A4 | 快捷键肌肉记忆 | MobaXterm 的 30 个快捷键中，≥ 28 个在 WindTerm 中行为相同 |
| A5 | 核心流迁移 | 用户在**不看文档**的情况下完成 FLOW-2（排障）与 FLOW-3（改配置） |
| A6 | 心理落差 | 用户对「是否愿意继续使用」打分 ≥ 4/5 |

### 7.3 不通过时的处置

- A1/A2 不通过 → 阻塞发布，修导入器。
- A3/A4 不通过 → 阻塞发布，修默认值（不是让用户自己调）。
- A5 不通过 → 阻塞发布，修可发现性（不是写文档）。
- A6 不通过 → 不阻塞发布，但必须记录原因并进入 M3 的首要事项。
