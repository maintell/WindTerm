# 03 · 需求编号与优先级体系

## 1. 为什么需要一套刻板的规则

这个项目的需求来源是**另一个产品的功能列表**，天然会滑向两种失败：

- **照抄病**：MobaXterm 有的都做，包括那些因为历史包袱才存在的东西（Xorg 版本选择、Rlogin、mathomatic），以及那些依赖外部重资产的（X11 转发）。
- **自由发挥病**：每遇到一个功能就重新讨论「我们要不要做、怎么做」，讨论结论散落在 issue 和聊天记录里，三个月后无人可查。

本文件的作用是把这两种情况都堵死：**每一条需求必须有 ID、有优先级、有决策、有验收标准、有来源。**
没有 ID 的需求不进路线图；没有验收标准的需求不算完成。

## 2. ID 规范

```
<域>-<三位序号>            例：SES-014
<域>-<三位序号>.<子项>     例：SES-014.1（仅用于需要单独验收的分解项）
```

### 域划分

| 域 | 覆盖 | 文档 |
|---|---|---|
| `SES` | 会话类型、会话树、导入导出、跳板机、代理、重连、连接诊断 | `spec/05` |
| `TER` | 终端仿真、标签/分屏、多执行、搜索、高亮、日志、宏、快捷键 | `spec/06` |
| `FIL` | SFTP/SCP/FTP 传输、文件浏览器、编辑器、Diff、图片查看 | `spec/07` |
| `GUI` | RDP、VNC、图形会话截图（X11/XDMCP 已作废，见 `spec/04` §12.6） | `spec/08` |
| `NET` | 端口转发、隧道管理、内置服务端、端口诊断、抓包 | `spec/09` |
| `LOC` | 本地终端、POSIX 路径命名空间、内置工具集、CLI 开关 | `spec/10` |
| `SEC` | 主密码、保险库、密钥、主机校验、审计、企业策略 | `spec/11` |
| `SET` | 设置模型、主题、快捷键、配置存储、便携模式、国际化 | `spec/12` |
| `EXT` | 插件包、包管理器、仓库与签名、定制器 | `spec/12` |
| `SYS` | 托盘、协议处理、外壳扩展、单实例、自动更新、多平台打包、可访问性 | `spec/12` `spec/13` |
| `NFR` | 非功能：性能、可靠性、安全基线、兼容性、可维护性 | `spec/13` |

### 硬规则

1. **ID 永不复用。** 需求作废时保留 ID，状态标 `⛔ 作废`，并写一句作废原因。历史提交信息、issue、ADR 都引用 ID，复用会让引用指向错误的东西。
2. **序号不要求连续。** 预留空隙（每域从 001 开始，按 10 递增也可）便于后续插入而不重排。
3. **一条需求只描述一件事。** 出现「并且」「同时」「以及」就要考虑拆分——因为验收时无法判断「部分完成」。
   - ❌ `SES-030：支持 SSH 跳板机并且支持 SOCKS 代理`
   - ✅ `SES-024：SSH 跳板机`、`SES-026：SOCKS/HTTP 代理`
4. **需求写「可观察的行为」，不写「实现方式」。** 实现方式属于 `design/`。
   - ❌ `SES-031：用 russh 的 direct-tcpip 实现跳板`
   - ✅ `SES-024：用户可为一个连接指定前置 SSH 主机，连接时自动经其转发`

## 3. 优先级判定

### 3.1 判定流程

对每条需求依次回答，**第一个「是」决定优先级**：

```
Q1 去掉它，FLOW-1~6 中是否有流程走不通？
   └ 是 → P0
Q2 去掉它，用户是否有「不引入新工具」的替代路径？
   └ 否 → P0
   └ 是 → 继续
Q3 它是 MobaXterm 用户日常高频使用（≥ 每天一次）的能力吗？
   └ 是 → P1
Q4 它是否只在特定场景（特定协议、特定 OS、特定设备）才用得到？
   └ 是 → P2
Q5 它的实现成本是否显著高于它带来的价值（含许可/专利/维护负担）？
   └ 是 → P3 或 NO（必须写理由）
   └ 否 → P1
```

### 3.2 优先级定义（与 `docs/README.md` 一致）

| 标记 | 含义 | 交付承诺 |
|---|---|---|
| `P0` | 必须 | **MVP（M1）不包含它就不能发布**。缺失时产品不可用，不是「体验差」 |
| `P1` | 重要 | **v1.0（M2）目标**。缺失会造成明确的能力落差，用户能感知到「不如 MobaXterm」 |
| `P2` | 增强 | v1.x。对标加分项、体验优化、特定场景覆盖 |
| `P3` | 观察 | 记录不排期。需要时重新评估 |
| `NO` | 不做 | 明确排除，必须写理由，且写进 `spec/01` §3.2 反目标或本文 §7 排除清单 |
| `ALT` | 替代实现 | 不照搬 MobaXterm 机制，用不同方式达成同等或更好结果，必须写差异与理由 |

### 3.3 兼容性分级（`ALT` 专用）

当一条需求标记为 `ALT` 时，必须同时标注兼容性等级，让用户知道迁移后行为差异：

| 等级 | 含义 | 用户影响 |
|---|---|---|
| `C1 完全兼容` | 行为、配置项、数据格式都与 MobaXterm 一致 | 无感迁移 |
| `C2 等价` | 能力相同，交互或命名不同 | 需要重新学一次，但不损失能力 |
| `C3 部分` | 覆盖主要用法，少数边缘用法不支持 | 需要针对边缘场景找替代方案 |
| `C4 不兼容` | 我们提供了不同机制，原机制不保留 | 需要改工作流 |

示例：
- `SES-20` MobaXterm 会话导入 → `C1`（数据格式兼容）
- `LOC-02` `/drives` 路径 → `ALT / C2`（我们用虚拟命名空间 + 自有 shell，PowerShell 里不能直接用 `/drives/c`）
- `LOC-003` `/registry` 虚拟目录 → `ALT / C4`（改用 `wt reg` CLI + GUI 查看器，不引入文件系统驱动）

## 4. 需求条目模板

`spec/05`~`spec/12` 中每条需求按此结构书写。字段缺一即视为未完成。

```markdown
### SES-024 · SSH 跳板机（Jump Host）

| 字段 | 值 |
|---|---|
| 优先级 | P0 |
| 兼容性 | C1 完全兼容 |
| 来源 | MobaXterm 文档 4.10 / 特性页 "SSH gateway" |
| 依赖 | SES-001（SSH 会话）、SEC-03（密钥） |
| 状态 | 🔁 待评审 |

**描述**
用户可以在任意连接（SSH/Telnet/RDP/VNC/SFTP）上指定一个前置 SSH 主机；
建立连接时先连前置主机，再经其 `direct-tcpip` 通道连到目标。

**行为规格**
1. 前置主机本身是一个完整会话（可再指定自己的前置主机，最多 5 跳）
2. 认证复用：优先复用已建立的同主机连接（连接池）
3. ...

**异常与边界**
| 情况 | 期望行为 |
|---|---|
| 前置主机不可达 | 报错指明「第 1 跳（bastion:22）连接超时」 |
| ... | ... |

**配置项**
| 键 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `jump.host` | string | 空 | 前置主机会话 ID |
| ... | | | |

**验收标准**
- [ ] AC-1 给定 A→B→C 三跳配置，当建立到 C 的连接时，B 上 `ss -tnp` 可见来自 A 的 SSH 连接且目标为 C:22
- [ ] AC-2 给定第 2 跳认证失败，错误信息包含跳数与主机名
- [ ] AC-3 给定前置连接已存在，建立第二条经同一前置的连接时，前置主机 SSH 连接数不增加

**设计映射** → `design/10` §3
```

### 验收标准的写法

必须是**可执行断言**，三种允许形式：

| 形式 | 适用 | 例子 |
|---|---|---|
| 给定/当/则（Given-When-Then） | 交互行为 | 给定远端 `sshd_config` 关闭 `AllowTcpForwarding`，当用户启动隧道，则报错指明该项并给出配置行 |
| 数值断言 | 性能、容量、精度 | 当粘贴 1 MB 文本，则终端在 2 s 内完成回显且不丢字节 |
| 状态断言 | 数据、持久化、并发 | 当导入 47 个会话时，`sessions` 表新增 47 行且 `folder_id` 层级与源文件一致 |

**不接受**的写法：`体验流畅`、`正确显示`、`性能良好`、`兼容各种场景`。

## 5. 需求状态机

```
⬜ 草案 ──评审通过──> 🔁 待评审 ──进入里程碑──> 🚧 实现中 ──代码合并──> ✅ 已实现 ──E2E 通过──> ✅ 已验证
   │                      │                                                                    │
   └──放弃──> ⛔ 作废      └──放弃──> ⛔ 作废                                              └──回归失败──> 🚧 实现中
```

| 状态 | 进入条件 | 谁可以改 |
|---|---|---|
| ⬜ 草案 | 有人写下它 | 任何人 |
| 🔁 待评审 | 模板字段齐全 | 需求作者 |
| 🚧 实现中 | 已排入里程碑且有负责人 | 负责人 |
| ✅ 已实现 | 代码合并 + 单元/集成测试通过 | 负责人 |
| ✅ 已验证 | 对应 AC 的 E2E 用例在 CI 上绿 | CI 自动 |
| ⛔ 作废 | 有书面理由 | 需 ADR 或评审记录 |

**关键约束：`✅ 已验证` 只能由 CI 置位，不能人工声明。** 这是防止「我觉得做完了」的唯一手段。

## 6. 需求 → 设计 → 测试 的追溯

三向链接是强制的，`design/15` 有一条结构测试会检查闭合性：

```
spec/04（矩阵）  ──ID──>  spec/05~12（规格）  ──ID──>  design/*（设计）
                                │                          │
                                └────── AC ───────────────>┘
                                          │
                                          ▼
                                  tests/e2e/*（用例名带 ID）
```

检查规则（CI 中执行）：
1. 每个 `P0`/`P1` 需求 ID 必须至少在 `design/` 中出现一次（否则「无设计承接」）；
2. 每个 `design/` 文档声明的需求 ID 必须存在于 `spec/`（否则「无来源设计」）；
3. 每个 `P0` 需求必须有至少一条 `AC-*`（否则「不可验收」）；
4. 每条 AC 必须能对应到一个测试标识（测试名或 `#[test]` 上的 `#[req(SES-024)]` 注解）；
5. `spec/04` 中不允许出现「待定」「TBD」——必须给出决策。

## 7. 排除清单（`NO` 的集中登记）

所有 `NO` 决策集中在此，便于一次性回答「你们为什么不做 X」。

| 需求 | 内容 | 不做理由 | 替代路径 |
|---|---|---|---|
| `SES-03` | Rlogin 会话 | 协议已被 SSH 完全取代，服务端默认关闭，安全评审会直接否掉 | 用 SSH；若必须，用 `ssh -o` 兼容模式或 Telnet |
| `SES-04` | Rsh 会话 | 同上，且无加密 | 同上 |
| `GUI-27` | RDP RemoteApp（单应用发布） | 需要服务器端 RemoteApp 配置，使用面极窄；IronRDP 支持度不足【待验证】 | 用完整桌面会话 |
| `LOC-03` | `/registry` 虚拟目录 | 需要内核级虚拟文件系统（Dokan/WinFsp 驱动），为一个诊断场景引入驱动签名与兼容负担不成比例 | 提供 `wt reg get <path>` CLI 与 GUI 注册表查看器 |
| `LOC-21` | mathomatic（计算机代数系统） | 与本产品场景无关，属 MobaXterm 的历史遗留捆绑 | 用户可用 Python/`bc` |
| `LOC-22` | fdupes | 与远程运维无关 | 用户可用系统工具 |
| `NET-10` | 内置 Telnet 服务端 | 明文协议，提供它等于提供一个后门；内置服务端的价值在「临时给同事传文件/临时 SSH 进来」，Telnet 服务端没有这种场景 | 用内置 SSH/SFTP 服务端 |
| `NET-11` | 内置 TFTP 服务端 | 使用面极窄（只用于网络设备固件升级），且 TFTP 无认证 | 用系统工具；提供 `wt tftp serve` 作为 P3 插件 |
| `GUI-32` | 远程桌面会话录制 | 涉及大量视频编码与存储，且录制他人桌面有合规风险 | 用系统级录屏工具 |
| — | 遥测 / 崩溃上报 | 违反「离线优先」与「不持有用户数据」原则 | 用户主动导出诊断包 |

> 注：`SES-03`/`SES-04` 在矩阵中同时保留了 `P3` 的「兼容读取」能力——**能导入并显示这类会话（灰显 + 提示不支持），但不实现连接**，避免迁移时数据丢失。

## 8. 变更流程

### 8.1 什么时候需要 ADR

以下任一情况，**必须先写 ADR 再改规格**：

- 影响跨模块接口（例如「终端数据走 IPC 还是共享内存」）
- 影响数据格式或存储位置（会话库、凭据格式、配置格式）
- 影响安全模型（加密算法、凭据存储、权限模型、网络监听）
- 影响许可或分发方式（引入 GPL 组件、改变主包内容）
- 改变优先级（`P0` ↔ `P1`）且影响里程碑
- 推翻已有 ADR

### 8.2 不需要 ADR 的变更

- 文案、图标、颜色
- 同一模块内部的实现细节替换（不影响接口）
- 性能优化（不改变可观察行为）
- 新增 `P3` 需求（先登记，不排期）

### 8.3 规格变更的最小动作

1. 改 `spec/04` 矩阵中该行的决策与优先级；
2. 改对应 `spec/05~12` 的条目；
3. 若有 ADR，在 `appendix/a-adr-index.md` 新增一条并互相引用；
4. 若影响里程碑，改 `spec/14`；
5. 在提交信息中带需求 ID（`feat(SES-024): ...` / `docs(SES-024): ...`）。

## 9. 非功能需求的特殊约定

`NFR-*` 与功能需求的区别在于**它们没有「做完了」这个状态，只有「达标/不达标」**。因此：

- 每条 `NFR` 必须给出**可测量的阈值 + 测量方法 + 测量环境**；
- `NFR` 的验收在 CI 中做成**回归门禁**（性能回归即失败），而不是一次性测试；
- 阈值必须写清「在什么条件下」，否则无法判定（例：`启动 < 1.2s` 必须说明「SSD、8 个会话、冷启动」）。

模板：

```markdown
### NFR-001 · 冷启动时间

| 字段 | 值 |
|---|---|
| 阈值 | ≤ 1200 ms（P95） |
| 测量点 | 进程创建 → 主窗口可接受键盘输入（首个终端渲染完成且 input 已绑定） |
| 环境 | Windows 11 / 4 核 / 16 GB / SSD / 预置 8 个会话 / 冷缓存 |
| 方法 | `wt bench startup --runs 30 --json`，取 P95 |
| 门禁 | 超过阈值 15% 连续 2 次构建 → CI 失败 |
```
