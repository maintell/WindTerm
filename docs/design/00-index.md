# 第二册 · 详细设计 · 索引

## 本册要解决的问题

规格回答「做什么」，设计回答「怎么做」以及**为什么不是别的做法**。

一份没有「为什么不是别的做法」的设计文档，等于把决策成本转嫁给未来的维护者——他们不知道某个约束是刻意的还是历史遗留，于是要么不敢改，要么改坏。所以本册每个关键决策都有：

1. **备选方案**（至少两个）
2. **否决理由**（具体的，不是「不合适」）
3. **代价声明**（这个选择牺牲了什么）
4. **ADR 链接**（可追溯）

## 与规格的双向链接

```
spec/04（矩阵，244 条）
   │ 每个 ID
   ▼
spec/05~12（规格，含 AC）
   │ 「设计映射」小节
   ▼
design/01~16（本文档，含实现细节）
   │ 每个文档开头「实现需求：...」
   ▼
tests/（用例名带 ID）
```

`design/15` §6 的结构测试会检查这条链是否闭合。**没有需求来源的设计是过度设计，没有设计承接的需求是空话。**

## 全册共同约定

### 代码引用

文档中的代码是**示意**，不是最终实现。它必须满足：

1. 类型与签名与真实设计一致（不能出现「文档里叫 A、代码里叫 B」）；
2. 关键算法与常量与实现一致（这些是设计的实质部分）；
3. 可以省略错误处理的样板，但不能省略**安全性相关**的处理。

### 待验证标记

`【待验证】` 表示该结论依赖尚未实测的技术假设。**M0 结束前必须清零**（`spec/14` §2.2）。
当前存在的待验证项集中在这几处：

| 位置 | 内容 | 验证方式 |
|---|---|---|
| `01` §4.1 | `russh` 的 `tcpip-forward` / agent 能力 | M0/S4 |
| `03` §6 | xterm.js 在 20 MB/s 下的丢字节与帧率 | M0/S2 |
| `08` §7 | OS 窗口捕获的帧率与稳定性 | M0/S5 |
| `07` §2.1 | IronRDP 的 AVC444 支持 | M0/S3 |
| `02` §3.4 | Tauri `ipc::Response` 的原始字节直通 | M0/S1 |
| `04` §6.2 | MobaXterm ini 的 `SubRep` 语义与字段名 | M0/S6 |
| `06` §4.1 | OpenSSH 9.x 的 scp 自动探测方式 | M0/S6 |

### 数字的来源

文档中的性能数字分三类，必须区分：

| 类型 | 标记 | 例 |
|---|---|---|
| **目标**（规格承诺） | 无标记 | 「吞吐 ≥ 20 MB/s」 |
| **实测**（已验证） | 标注「实测」+ 日期 + 环境 | 「实测 2026-11-02，Win11/4核，72 MB/s」 |
| **估算**（未验证） | 标注「估算」 | 「窗口 64 时约 75 MB/s（估算）」 |

**禁止把估算写成实测。** 这是文档可信度的底线。

## 已知的设计债务

诚实记录，避免被误认为「已经想清楚了」：

| # | 债务 | 影响 | 计划 |
|---|---|---|---|
| D1 | 终端状态在前端，Rust 拿不到屏幕内容 | 无法做服务端搜索、会话录制、多客户端共享 | v2 引入 `wt-term::GridModel`（ADR-0004 已留接口） |
| D2 | 终端 CJK 列宽/输入法在 xterm.js 下可能不达标 | 中文用户全屏程序错位 | M0/S5 验证；备选 Rust 终端内核 |
| D3 | rsync 块级差分只在「双方都有 rsync」时可用 | 大文件小改动场景体验差 | 接受；UI 明确显示模式 |
| D4 | ZMODEM 未实现 | 少数只能走终端通道的场景不支持 | M3（P2） |
| D5 | 进程插件无沙箱 | 安全边界靠用户判断 | 接受（技术上不可行），靠签名与策略缓解 |
| D6 | MobaXterm 密码无法导入 | 迁移需重新输入凭据 | 分组批量套用（ADR-0010） |
| D7 | 单文件 > 20 MB 不能在编辑器打开 | 大日志只能下载 | 接受（编辑器不是日志查看器） |
