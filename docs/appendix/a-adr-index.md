# 附录 A · 架构决策记录（ADR）索引

## 使用规则

**什么时候必须写 ADR**（`spec/03` §8.1）：

- 影响跨模块接口
- 影响数据格式或存储位置
- 影响安全模型
- 影响许可或分发方式
- 改变优先级且影响里程碑
- 推翻已有 ADR

**不需要 ADR**：文案、图标、颜色、模块内实现替换、不影响可观察行为的性能优化。

**格式**：每条 ADR 必须有 状态 / 背景 / 决策 / 后果 / 备选方案 / 风险。缺「备选方案与否决理由」的 ADR 不予接受——那是命令，不是决策记录。

## ADR-0001

### 采用 Tauri 2 + Rust 核心

| 字段 | 值 |
|---|---|
| 状态 | ✅ 已接受 |
| 日期 | 2026-11-02 |
| 决策者 | 项目发起人 |
| 相关 | `design/01`、`design/02`、ADR-0008 |

**背景**

需要一个跨 Windows/macOS/Linux 的桌面应用，同时满足：
- 终端高频渲染（`NFR-003`：20 MB/s 不卡）；
- 网络协议栈（SSH/RDP/VNC）实现自由；
- 安装包尽量小（`NFR-022`：≤ 45 MB）；
- 内存占用低（`NFR-002`：3 会话 ≤ 150 MB）。

**决策**

UI 用 WebView（Tauri 2 提供），所有非 UI 逻辑用 Rust。连接、缓冲、凭据、协议全部在 Rust 主进程；WebView 只做渲染与输入。

**后果**

| 正面 | 负面 |
|---|---|
| 安装包小（无内嵌 Chromium，Win 用系统 WebView2） | 依赖系统 WebView，Linux 上 WebKitGTK 版本碎片化 |
| Rust 侧内存安全，协议栈可审计 | Rust 编译时间较长，团队需要 Rust 能力 |
| 一套代码三平台 | 三平台 WebView 行为差异（需 S8 验证） |
| 核心与 UI 分离，CLI 可复用 | IPC 需要精心设计（ADR-0005） |

**备选方案与否决理由**

| 方案 | 否决理由 |
|---|---|
| Electron | 安装包 100 MB+、空闲内存 300 MB+，与「轻量替代 MobaXterm」定位直接冲突；且 Node 侧做 50 并发会话的内存管理不如 Rust |
| 纯 Rust GUI（egui / iced） | 终端渲染、富文本编辑、i18n 排版、可访问性全部要自研，M1 无法交付 |
| Qt（C++/PySide） | 许可（商业授权或 LGPL 动态链接）与跨平台打包复杂度高；团队栈不匹配 |
| Wails（Go） | Go 的 SSH/RDP 生态弱于 Rust（IronRDP、russh 无对等替代） |
| Flutter | 桌面端生态不成熟；终端渲染需自绘 |

**风险**

| 风险 | 缓解 |
|---|---|
| WebKitGTK 差异 | M0/S8 验证；必要时限定支持发行版或改用 CEF |
| WebView2 缺失 | 安装时引导下载（`design/14` §4.1） |
| Rust 人才 | 分层设计让协议层可独立开发；CLI 降低 UI 依赖 |

## ADR-0002

### ~~X Server 作为外部 provider~~（已被 ADR-0012 取代）

| 字段 | 值 |
|---|---|
| 状态 | ⛔ **已作废**（2026-11-02，由 ADR-0012 取代） |
| 原日期 | 2026-11-02 |
| 相关 | `design/08`（已重写为 VNC）、`spec/08`（已重写为远程桌面）、ADR-0007、ADR-0012 |

> **保留本文而不是删除**：这个决策曾经成立，并且是当时最合理的取舍。删掉它会让后来者以为「一开始就没考虑过 X11」，
> 从而重复讨论「要不要支持 X11」。保留 + 标注作废原因，才是决策记录应有的样子。

**原背景**

MobaXterm 的核心卖点之一是内置 X Server（移植 Xorg 到 Windows）。当时的结论是不自研，而是定义 `XServerProvider` 抽象，
支持 VcXsrv / XQuartz / 系统 Xorg / 已有 DISPLAY / 用户自定义命令，主程序只做管理、转发、桥接。

**原决策（已废止）**

不实现 X 协议服务端，改为 provider 抽象。

**为什么废止**

原决策解决的是「我们写不出 X Server」这个问题，但它没有解决更根本的问题：**即使把 X Server 外包出去，体验仍然不可控**。

| 原以为的问题 | 实际的问题 |
|---|---|
| 自研 X Server 成本太高 | 成本确实高，但这不是主要障碍 |
| 用 provider 就能绕开 | provider 的 rootless 行为、扩展支持、OpenGL、中文输入法全部由第三方决定，我们既不能修也不能保证 |
| 用户装一次就好 | 三平台各装一个不同的 X Server；企业环境还要过 GPL 与安全评审；首次使用就多一道断点 |

**取代它的决策**：整体移除 X11 能力（ADR-0012）。用户的替代路径是「自装 X Server + 系统 `ssh -X`」。

**从这次作废中得到的教训**（写进 `spec/03` §1 的「照抄病」）

> 对标一个产品时，容易把「它有的功能」当成「用户需要的功能」。
> 正确的问法是：**这个功能的价值，是否依赖于一个我们无法控制的组件？** 如果是，那它不是我们的功能。

## ADR-0003

### 不打包 POSIX 运行时

| 字段 | 值 |
|---|---|
| 状态 | ✅ 已接受 |
| 日期 | 2026-11-02 |
| 相关 | `design/11`、`spec/10` §1 |

**背景**

MobaXterm 打包 Cygwin，因此本地终端是真正的 bash，能跑 `gcc`、`make`、`rsync`。

**决策**

不打包 Cygwin/MSYS2。提供三条并列路径：
1. **WindShell**（自研，内置，POSIX 风格语法）；
2. **系统 shell**（PowerShell / cmd / Git Bash）；
3. **WSL**（检测到则推荐）。

内置 `uutils/coreutils` 提供基础工具；`grep`/`sed` 自研；`awk` 不提供（明确告知）。

**后果**

| 正面 | 负面 |
|---|---|
| 安装包 +8 MB 而非 +250 MB | 不支持 `fork()` 型工具（`make`、`gcc`、`configure`） |
| 无 GPL 传染 | shell 语法不完整（无函数、数组、`trap`） |
| 路径语义统一（`/drives` 由我们定义） | 需要用户理解「这个环境能做什么、不能做什么」 |
| 无 `fork()` 模拟的性能损耗 | 老 MobaXterm 用户的脚本可能需要改写 |

**备选方案与否决理由**

| 方案 | 否决理由 |
|---|---|
| 打包 Cygwin | 体积、GPL、`fork` 性能、两套路径语义（与 ADR-0007 冲突） |
| 打包 MSYS2 | 同上 |
| 只支持系统 shell | 丢失 `ls`/`grep` 等基础工具，MobaXterm 用户会立刻感到缺失 |
| 内嵌 Linux 虚拟机 | 完全不成比例 |

**风险**

| 风险 | 缓解 |
|---|---|
| 用户期望落差 | UI 明确说明能力边界；运行不支持的命令时给出具体建议 |
| 自研 shell 的 bug | 词法/语法/展开有完整单测；不支持语法给明确错误而非静默失败 |
| `awk` 缺失 | 检测系统 `awk`/`gawk`；都没有则明确告知（不提供残缺实现） |

## ADR-0004

### 终端内核用 xterm.js

| 字段 | 值 |
|---|---|
| 状态 | ✅ 已接受（**有条件**：M0/S2 实测不达标则切换） |
| 日期 | 2026-11-02 |
| 相关 | `design/03`、`spec/06` §1.1 |

**背景**

终端是本产品使用时长最高的界面。VT 解析放前端还是 Rust，决定了整个终端子系统的形状。

**决策**

v1 用 `@xterm/xterm` 5.x（WebView 内）作为 VT 解析与渲染内核。Rust 侧只做传输、环形缓冲、ANSI 剥离、控制序列嗅探。

保留 `TerminalBackend` trait 与 `wt-term::GridModel` 空实现，为 v2 切换到 Rust 内核留接口。

**后果**

| 正面 | 负面 |
|---|---|
| conformance 已被大量产品验证，不需要自研 6~12 人月 | Rust 拿不到屏幕内容（搜索/日志/跟随路径需另设通路） |
| 渲染器（WebGL/Canvas/DOM）现成 | 大量输出时有性能天花板 |
| 输入编码（DECCKM/bracketed paste）现成 | 内存随滚动缓冲增长（JS 堆） |

**切换条件（必须明确，否则这个 ADR 等于没约束）**

M0/S2 实测，满足以下任一条件即启动切换：
- 20 MB/s 持续输出时丢字节；
- UI 帧率 < 30 fps 且无法通过流控改善；
- 输入延迟 > 100 ms。

**备选方案与否决理由**

| 方案 | 否决理由 |
|---|---|
| 自研 Rust 终端内核（vte + 网格 + 自绘） | 6~12 人月；vttest 全绿周期不可控；M1 交付不了 |
| 双解析（前后端各一份） | 状态必然不同步（前端显示正常、日志错位） |
| 用 `alacritty_terminal` 复用其网格 | 渲染仍需自研；且它的网格模型与我们的需求（高亮、跟随路径）不完全匹配 |

**风险**

| 风险 | 缓解 |
|---|---|
| 性能不达标 | S2 提前验证；流控（`TER-034`）保证「慢但不丢」 |
| 内存增长 | 缓冲上限 + 淘汰策略 |
| 迁移成本 | `TerminalBackend` trait 隔离 |

## ADR-0005

### 拉取式二进制 IPC

| 字段 | 值 |
|---|---|
| 状态 | ✅ 已接受 |
| 日期 | 2026-11-02 |
| 相关 | `design/02` §3.4、§5 |

**背景**

终端与 RDP 帧是高频大数据（20 MB/s、30~60 fps）。Tauri 默认的 IPC 是 JSON，传二进制需要 base64（+33%）或数组（+300%）。

**决策**

三层 IPC：
- **Command**（JSON）——低频动作；
- **Event**（JSON，节流）——状态变更；
- **Pull**（二进制响应）——终端数据与帧数据，由前端每帧主动拉取。

**后果**

| 正面 | 负面 |
|---|---|
| 无 base64 开销 | 前端需要写拉取循环 |
| 背压是结构性的（不拉就不发） | 拉取与渲染的时序需要调（空结果等下一帧） |
| 单消费者模型与「一会话一渲染归属」一致 | 多窗口共享同一会话需要切换 owner |

**备选方案与否决理由**

| 方案 | 否决理由 |
|---|---|
| 全 JSON + base64 | 33% 带宽浪费 + 编码开销；20 MB/s 下 CPU 明显 |
| 本地 WebSocket | 需要监听端口（安全面）、需要自己实现背压、多一层协议 |
| 共享内存 + 环形缓冲 | 性能最好，但 WebView 无法直接读共享内存（需要 SharedArrayBuffer + COOP/COEP 配置，Tauri 下不稳定） |
| 推送 + 限流 | 核心不知道前端处理能力，限流阈值只能猜 |

**风险**

| 风险 | 缓解 |
|---|---|
| Tauri `ipc::Response` 的原始字节直通未实测 | M0/S1；若不可用则退到 WebSocket |
| 拉取频率与帧率耦合 | 用 `requestAnimationFrame` 对齐 |

## ADR-0006

### SQLite + TOML 分离存储

| 字段 | 值 |
|---|---|
| 状态 | ✅ 已接受 |
| 日期 | 2026-11-02 |
| 相关 | `design/04` §1 |

**背景**

MobaXterm 用单一 INI 文件存全部数据，代价是：导入导出易半途失败、并发写丢数据、无法表达嵌套（`[Bookmarks_1]` 平铺编号）。

**决策**

- 设置 → TOML 文件（可读、可 diff、可进 Git、可企业下发）
- 会话/隧道/宏/队列 → SQLite（事务、索引、并发）
- 凭据 → 加密二进制（ADR-0009）

**后果**

| 正面 | 负面 |
|---|---|
| 设置可手改且保留注释（`toml_edit`） | 两种存储需要两套备份/迁移逻辑 |
| 导入是单事务，要么全成要么全败 | 用户不能再用文本编辑器直接改会话（需提供导出） |
| 会话可查询（按 host、按最近使用） | 需要 SQLite 依赖（bundled，+1.5 MB） |

**备选方案与否决理由**

| 方案 | 否决理由 |
|---|---|
| 全 SQLite | 设置无法 diff/手改/企业下发 |
| 全文件（JSON/TOML） | 导入无事务、并发写覆盖、查询要全量加载 |
| 全 INI（兼容 MobaXterm） | 无法表达嵌套，解析器易错；我们仍要写 ini **导入**器，但不用它做主存储 |

## ADR-0007

### GPL 组件不随主包分发

| 字段 | 值 |
|---|---|
| 状态 | ✅ 已接受 |
| 日期 | 2026-11-02 |
| 相关 | `spec/01` §5、`design/14` §3 |

**背景**

必需的第三方能力中，仍有 GPL 成分：MSYS2 运行时（桥接用途，可选）。**X Server（VcXsrv / Cygwin-X）与 X11 窗口管理器已不在清单内**——X11 能力整体移除（ADR-0012）。

**决策**

主安装包采用 **Apache-2.0**，**不包含**任何 GPL 二进制。GPL 组件通过两条途径提供：
1. 用户自行安装（我们只检测与引导）；
2. 单独的「GPL 组件包」（独立下载、独立许可提示、独立安装）。

**后果**

| 正面 | 负面 |
|---|---|
| 主包许可干净，企业可采用 | 用户多一步安装 |
| 不承担 GPL 源码提供义务（对主包而言） | 需要维护两条分发路径与两套文档 |
| 企业可自带已批准的 POSIX 桥接组件 | 首次使用体验有断点（仅在使用 MSYS2 桥接时） |

**备选方案与否决理由**

| 方案 | 否决理由 |
|---|---|
| 整体 GPL-3.0 | 企业采用率显著下降；与「可审计、可内部分发」的目标冲突 |
| 打包 GPL 二进制但声明「mere aggregation」 | 法律边界模糊（同进程/紧耦合的判定），不值得冒险 |
| 完全不用 GPL 组件（自研 POSIX 兼容层） | 见 ADR-0003，代价过高；且 MSYS2 桥接是可选能力，不做也不影响主流程 |

**风险**

| 风险 | 缓解 |
|---|---|
| 用户不清楚为什么要装两个东西 | 引导页解释清楚「MSYS2 是独立程序，采用 GPL 许可」 |
| GPL 组件包本身合规 | 随包提供完整源码与许可文本；不修改上游代码 |

## ADR-0008

### 前端采用 SolidJS

| 字段 | 值 |
|---|---|
| 状态 | ✅ 已接受 |
| 日期 | 2026-11-02 |
| 相关 | `design/13` §1 |

**背景**

UI 需要处理高频状态更新（终端状态、传输进度、帧率），且要在低端机上保持流畅。

**决策**

SolidJS + TypeScript + Vite。

**后果**

| 正面 | 负面 |
|---|---|
| 细粒度响应式，无 VDOM diff，高频更新成本低 | 生态小于 React（但我们的重组件都是自研或用专用库） |
| 运行时 ~7 KB | 团队需要学习（语法接近 React hooks，成本可控） |
| 编译时优化，产物小 | 部分第三方组件需要适配层 |

**备选方案与否决理由**

| 方案 | 否决理由 |
|---|---|
| React | VDOM diff 在 60 fps 高频更新下 CPU 明显；产物更大 |
| Svelte 5 | 可选，但 runes 生态尚新；Solid 的信号模型更贴近我们的需求 |
| Vue 3 | 响应式好，但模板编译产物与工具链复杂度高于 Solid |
| 原生 TS + 手写 DOM | 开发效率过低，M1 交付不了 |

**风险**

| 风险 | 缓解 |
|---|---|
| 生态不足 | 关键组件（虚拟列表、树、对话框、表单）自研，约 2000 行 |
| 人才 | Solid 与 React 的心智模型接近，迁移成本低 |

## ADR-0009

### 自研保险库格式

| 字段 | 值 |
|---|---|
| 状态 | ✅ 已接受 |
| 日期 | 2026-11-02 |
| 相关 | `design/09` §1、`spec/11` §4.2 |

**背景**

凭据存储需要：主密码保护、跨机器迁移、可审计、可被第三方脚本恢复。

**决策**

自研容器格式：`magic + header(JSON) + AEAD 密文`；KDF 用 Argon2id（参数自适应），AEAD 用 XChaCha20-Poly1305，AAD 绑定 header。**格式公开**。

**后果**

| 正面 | 负面 |
|---|---|
| 格式公开 → 用户可自己恢复（`spec/11` §4.2 有规范） | 自研意味着需要严格测试（密码学代码出错代价极高） |
| 参数写进文件头，可平滑升级 | 需要维护格式版本兼容 |
| 不依赖 OS 钥匙串，可跨机器 | 用户忘记主密码 = 数据无法恢复（必须明确告知） |

**备选方案与否决理由**

| 方案 | 否决理由 |
|---|---|
| `keyring` 只存 OS 钥匙串 | 无法跨机器迁移；Linux 上 libsecret 缺失时静默失败 |
| SQLCipher | 引入 C 依赖与编译变体（+3 MB）；只解决「数据库加密」，不解决条目模型 |
| `age` | 面向文件加密，不适合频繁增删条目的容器 |
| 直接用 `secrecy` + 明文文件 | 不满足 `NFR-010` |

**风险**

| 风险 | 缓解 |
|---|---|
| 实现 bug 导致数据不可恢复 | 写入前备份 `.bak`；轮换后验证可解密；Python 独立实现交叉验证 |
| 用户忘记主密码 | 设置时强提示；提供 hint 字段；文档明确「无法找回」 |
| 密码学误用 | 只用 `argon2` + `chacha20poly1305` 两个经过审计的 crate；不自研原语 |

## ADR-0010

### 导入策略：结构优先、凭据补录

| 字段 | 值 |
|---|---|
| 状态 | ✅ 已接受 |
| 日期 | 2026-11-02 |
| 相关 | `design/04` §6.3、`spec/05` §5.4 |

**背景**

从 MobaXterm 迁移是本产品的入场券（`spec/14` §7）。但 MobaXterm 的密码加密是未公开的私有实现。

**决策**

1. **MVP 阶段**：导入全部结构，凭据标记为「需重新输入」；
2. **提供「凭据补录向导」**：按 `(用户名, 认证方式)` 分组，每组输入一次密码即批量套用；
3. **M2 阶段**：若 M0/S6 用真实样本验证成功，再支持用主密码解密；
4. **永不**提供「导出为明文密码」。

**后果**

| 正面 | 负面 |
|---|---|
| 不依赖逆向工程，行为可预测 | 用户需要重新输入 3~5 次密码（而非 41 次） |
| 不引入「可能失败且无法解释」的解密代码 | 若用户只有一个密码且 41 台机器都用它，仍需输 1 次 |
| 凭据进入我们自己的保险库，安全模型统一 | — |

**备选方案与否决理由**

| 方案 | 否决理由 |
|---|---|
| 逆向 MobaXterm 加密算法作为主路径 | 不可靠（版本差异）、不可解释（失败时用户无法理解）、法律与伦理风险 |
| 让用户手工逐条重新输入 | 41 次输入 = 用户放弃迁移 |
| 不做导入，只支持手工新建 | 直接失去迁移用户 |

**风险**

| 风险 | 缓解 |
|---|---|
| 用户嫌麻烦 | 分组批量套用把成本压到分钟级；向导可跳过、可后补 |
| ini 格式版本差异 | M0/S6 用 3 个真实样本校准；未知字段保留在 `extra` 不丢 |

## ADR-0011

### 命名与商标风险处置

| 字段 | 值 |
|---|---|
| 状态 | 🔁 **待决策** |
| 日期 | 2026-11-02 |
| 相关 | `spec/01` §5.4 |

**背景**

GitHub 上已存在 `kingToolbox/WindTerm`——一个开源的 SSH/SFTP/串口终端，与本项目**同名且同赛道**。

**问题**

| 影响 | 说明 |
|---|---|
| 搜索可见性 | 用户搜 "WindTerm" 会先找到它 |
| 包名冲突 | Homebrew / winget / apt / AUR 的包名可能被占用 |
| 商标 | 若未来商业化，无法注册 |
| 用户混淆 | 「你们和那个 WindTerm 什么关系？」 |

**待决策的三个选项**

| 选项 | 优点 | 缺点 |
|---|---|---|
| **A. 保留 WindTerm，接受混淆** | 零成本、仓库名不变 | 搜索劣势长期存在；无法注册商标 |
| **B. 对外改用新名，内部代号不变** | 可注册、可建立独立品牌 | 需一次性改：二进制名、包名、协议 scheme、配置目录、文档标题 |
| **C. 保留 WindTerm，加副标题区分**（如 "WindTerm Studio"） | 改动小、部分区分 | 商标仍可能不可注册；搜索仍混淆 |

**建议**

选项 B，且**在写第一行产品代码之前定下来**。理由：改名成本随代码量线性增长——一旦发布过安装包、写过配置目录、注册过协议 scheme，改名就要做数据迁移。

**执行清单（若选 B）**

| 项 | 现值 | 影响 |
|---|---|---|
| 仓库名 | `Windterm` | 可保留 |
| crate 前缀 | `wt-` | 已与名称解耦，无需改 |
| 二进制名 | `wt` / `WindTerm` | 需改 |
| 包标识 | `dev.windterm.app` | 需改 |
| 协议 scheme | `windterm://` | 需改 |
| 配置目录 | `WindTerm` | 需改 |
| 文档标题 | WindTerm | 需改 |

**在决策前**：所有文档统一用 `WindTerm` 作为**代号**；代码中一律用 `wt-` 前缀（已与最终名解耦）；**不要**在任何对外渠道（包管理器、官网、社交）注册 `WindTerm` 相关标识。

**风险**

| 风险 | 缓解 |
|---|---|
| 一直不决策，越拖越贵 | 设为 M1 之前的阻塞项（`spec/14` §9 R6） |
| 新名与现有产品冲突 | 决策前做商标检索（目标市场 + 相关类别） |

## ADR-0012

### 移除 X11 相关能力

| 字段 | 值 |
|---|---|
| 状态 | ✅ 已接受 |
| 日期 | 2026-11-02 |
| 决策者 | 项目发起人 |
| 取代 | ADR-0002（X Server 作为外部 provider） |
| 相关 | `spec/04` §12.6、`spec/08`、`design/08`、ADR-0007 |

**背景**

初版规格把 X11 转发、X Server provider、XDMCP 作为 P0 能力纳入（`GUI-001`~`GUI-014`、`SES-007`），
理由是 MobaXterm 把它当作核心卖点，而「替代 MobaXterm」意味着要覆盖它。

复核后发现三个问题：

1. **依赖不可控。** X11 转发必须有本地 X Server。Windows 要 VcXsrv、macOS 要 XQuartz、Linux 要用系统 Xorg——三者都是外部程序，我们既不能打包（GPL + 体积 + 驱动级兼容），也不能保证其行为。
2. **体验上限不在我们手里。** rootless 多窗口、扩展支持、OpenGL 加速、中文输入法，质量全部由第三方 X Server 决定。用户遇到问题时，我们既不能修也不能承诺修复时间。
3. **与产品前提冲突。** 「跨平台、开箱即用、零外部依赖」是本产品的三个前提（`spec/01` §2.4）。X11 与三者同时冲突，且收益面（现代 Linux 服务器上需要图形程序的场景）很小。

**决策**

**整体移除** X11 相关能力，共 15 条需求作废：

- `GUI-001`~`GUI-014`：X Server provider、X11 转发、多窗口、窗口化模式、标签内嵌、X 扩展、OpenGL、剪贴板、键盘与输入法、DISPLAY 管理、访问控制、多显示器、XDMCP、远程桌面环境启动
- `SES-007`：XDMCP 会话类型

同时移除：`wt-x11` crate、`XServerProvider` trait、`x11-req` / `x11` 通道处理、X11 Setup 握手、X11 剪贴板桥、X11 键盘映射与输入法方案、`x11` 会话类型、`-noX` / `--no-x11` 命令行开关。

**保留**：RDP（`GUI-015`~`GUI-027`）、VNC（`GUI-028`~`GUI-031`）、图形会话截图（`GUI-035`）、`SES-005`、`SES-006`。

**用户的替代路径**

在本地自装 X Server，然后 `ssh -X user@host` 到目标机。这条路径与我们无关，也不需要我们参与。
文档与 FAQ 必须给出这条路径，而不是让用户以为「这个功能坏了」。

**后果**

| 正面 | 负面 |
|---|---|
| 少一个 GPL 依赖，主包许可更干净（ADR-0007 的负担减轻） | 失去 MobaXterm 的招牌能力之一，对标表上出现明确空白 |
| 少一个「首次使用需额外安装」的断点，开箱即用成立 | 少数需要远端 GUI 的用户必须自己解决 X Server |
| 少一个最大的技术不确定性（原 M0/S4 的 `x11-req` 验证、S5 的输入法验证全部取消） | `spec/14` 的 M0 从 8 个 spike 降到 8 个（S4/S5 改为别的主题），风险清单重排 |
| 不再需要维护 X11 协议细节（Setup 握手、cookie、xauth 兼容） | — |
| 移除后 P0 从 47 降到 44，MVP 范围更收敛 | — |

**备选方案与否决理由**

| 方案 | 否决理由 |
|---|---|
| 维持 ADR-0002（provider 抽象） | provider 抽象解决的是「谁来实现 X Server」，没解决「体验由谁保证」。用户装不上、装错版本、输入法不工作，仍然是我们的口碑问题 |
| 自研最小 X Server | 至少 6 人年，且只能跑简单程序；现代 GTK/Qt 依赖大量扩展 |
| 保留但降级为 P2/P3 | 保留就要保留代码路径、文档、测试、依赖声明与支持承诺。一个「半支持」的 X11 比不支持更伤用户 |
| 只支持 Linux（用系统 Xorg） | 跨平台一致性被破坏；且 Linux 上 `ssh -X` 本来就是用户习惯，我们没有增量价值 |

**风险**

| 风险 | 缓解 |
|---|---|
| 对标表上出现空白，影响「替代 MobaXterm」的说服力 | 在 `spec/01` §2.2 与 §3.2 明确写出「不做及为什么」，并给出替代路径。诚实比假装完整更能建立信任 |
| 已按旧规格开工的读者困惑 | `spec/04` §12.6 保留全部作废 ID 与理由；ADR-0002 保留并标注作废；`design/08` 开头解释「曾经设计过、后来删了」 |
| 用户仍提出 X11 需求 | 记录在 `spec/04` §12.6 的「替代路径」列；若未来需求强烈，重新走 ADR（不复活旧 ID） |

**从这次决策中提炼的规则**（已写入 `spec/03` §1）

> 对标一个产品时，容易把「它有的功能」当成「用户需要的功能」。
> 正确的问法是：**这个功能的价值，是否依赖于一个我们无法控制的组件？** 如果是，那它不是我们的功能。
